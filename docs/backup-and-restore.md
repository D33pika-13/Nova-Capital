## Local tooling and command

`check:native-database` now needs reviewed PostgreSQL 17 server binaries plus `pg_dump` and `pg_restore`. It looks for clients in `POSTGRES_CLIENT_BIN_DIR`, falling back to `POSTGRES_BIN_DIR`. Missing clients fail the gate; restore is never silently skipped.

The optional builder downloads the official PostgreSQL 17.11 source archive and checks its pinned SHA-256 before extracting or executing build files. It builds only the client tools and their libraries in an owned temporary directory as an unprivileged user. It does not connect to a database, install a system service, change the application dependencies or install into system directories. Prerequisites are a C toolchain, make, tar/bzip2, bison/flex, Perl, OpenSSL development files and zlib. On macOS, set `POSTGRES_OPENSSL_ROOT` to a reviewed OpenSSL prefix if system headers/libraries are unavailable; that path must be a simple absolute path without spaces. The builder records its public build output in the owned directory.

```sh
export POSTGRES_CLIENT_MANIFEST=/absolute/path/to/a-new-client-tools.json
# Optional: export POSTGRES_OPENSSL_ROOT=/absolute/openssl-prefix
node scripts/build-postgres-test-clients.mjs
export POSTGRES_CLIENT_BIN_DIR="$(node --input-type=module -e 'import {readFileSync} from "node:fs"; console.log(JSON.parse(readFileSync(process.env.POSTGRES_CLIENT_MANIFEST,"utf8")).bin)')"
POSTGRES_BIN_DIR=/path/to/reviewed/server/bin pnpm check:native-database
```

Choose a new manifest path in an existing private directory; the builder refuses to overwrite a file. The printed manifest identifies the owned public-tool directory for reuse/removal. ## Rehearsal contract

`NativeRestoreRehearsal` runs only inside the existing native fixture after verifying its loopback endpoint, random cluster marker and exact temporary data directory. It creates synthetic admin/client mappings, exact-decimal financial records and actual application session/MFA/recovery state. It uses a password file with mode 0600 and a minimal subprocess environment, verified TLS and explicit loopback host/port. No arbitrary source/target URL is accepted and no environment file is loaded.

A read-only repeatable-read transaction exports the snapshot used by `pg_dump --format=custom`. A recovery code is consumed and its session revoked after that cut point, while the archive deliberately retains the earlier snapshot. This exercises the stale-authentication risk of point-in-time recovery. The archive is hashed before use and restored with `--single-transaction --exit-on-error` into a uniquely named fresh database in the same owned cluster. The helper uses no overwrite/clean/create-from-archive flag. Runtime/PUBLIC CONNECT is revoked before restore. Existing privileged owner access is reserved for this isolated rehearsal.

The rehearsal verifies:

- All public/private table counts and SHA-256 digests, including financial revisions, audit history, auth state and durable side-effect ledgers. JSONB text retains exact decimal values while hashing; no financial rows or protocol secrets are printed.
- Sequence values and definitions, columns/defaults/constraints, indexes, functions/security-definer/search-path settings, owners, RLS flags/policies, schema permissions and effective ACLs. PostgreSQL can omit an explicit ACL equal to its default; normalization includes those defaults and sorts grants rather than treating storage representation as a privilege change. CHECK expressions are reparsed/planned with PostgreSQL EXPLAIN output, without ANALYZE or scanning rows, to normalize associative expression grouping; names, validity, inheritance and deferrability remain strict. Parentheses are not stripped with a regex.
- A damaged archive is rejected before application tables appear. A deliberate target DDL conflict rolls back the entire restore and preserves its owned sentinel; valid restore then starts from an empty application schema.
- Runtime cannot connect during quarantine. Owner intent/environment/operation guards reject missing/wrong target, invalid environment and malformed operation IDs. Application-role execution is denied even when it sets those custom settings itself.
- Authentication quarantine preserves business data and every prior audit row, adds an operation audit, retains confirmed encrypted MFA factors, invalidates restored sessions/one-use state/recovery codes, and prevents old session/code reuse. After explicit reopening of only the owned test target, real runtime connections enforce anonymous/A/B isolation, private-table denial, exact decimal values and audit mutation denial.

PostgreSQL [documents pg_dump](https://www.postgresql.org/docs/17/app-pgdump.html) as a single-database backup; global roles/tablespaces are separate. The native source and target share existing cluster roles. This test does not establish cross-cluster role/password recreation, managed-service restore, concurrent sequence allocation guarantees, external authentication recovery, file/object recovery or an application-browser journey. The runner removes the owned cluster, archive, password file, synthetic credentials and TLS keys after success or failure. Public compiled tools remain reusable separately.

## Authentication quarantine operation

`supabase/operations/post-restore-quarantine.sql` is an owner operation outside the migration directory. It is never invoked automatically during normal startup, migrations or a customer request. Run it only on the reviewed isolated recovery target, with app/jobs/outbound providers disabled and owner access through an approved administration channel.

On that same owner session, deliberately set `nova.restore_target` to the exact destination database, `nova.restore_environment` to `test`, `staging` or `production`, and `nova.restore_operation` to the reviewed operation UUID. These settings record operator intent; they do not independently attest the hosting environment or authorize a production action. Review the destination/operation and obtain applicable authorization before a real restore or cutover. When using psql, enable `ON_ERROR_STOP`; execute the entire SQL file as one transaction and verify its audit row and resulting state before restoring application access.

The operation revokes all restored Entra sessions, deletes one-use login/MFA challenges and unfinished factors, consumes every remaining recovery digest and advances confirmed factors past the current/next TOTP step. Confirmed encrypted secrets remain enrolled. Allow the skipped authenticator windows to pass before attempting normal proof; after fresh primary sign-in and a fresh valid authenticator proof, users can regenerate recovery codes. Lost-all-proofs recovery still requires the reviewed operator identity-recovery process. There is no email-only bypass or master code. Each successful invocation appends an operation audit; it does not grant CONNECT, resume workers or declare cutover complete.

The durable scheduler-status view also treats the restore-quarantine audit as a new boundary: preserved pre-recovery run history does not establish freshness, and a newly started scheduled batch is required.

A database restore cannot undo prior SMTP acceptance, directory creation or externally issued credentials. The SQL operation does not revoke upstream Supabase/Entra provider sessions, reconcile suspended/admin accounts, repair missing post-backup intent ledgers, restore object bytes or invalidate already issued storage links. Keep access closed until those independent checks pass. Review external side effects against current provider evidence before enabling any send/create/retry path; never reset uncertainty simply to obtain a successful retry.
