# Technical specification — NOVA CAPITAL

## Current Entra selection contract

`AUTH_PROVIDER=supabase|entra` selects `AuthenticationFactory` and matching request-scoped identity, accounts, callback/MFA controllers and UI. Enabled Entra profiles require canonical HTTPS application origin, tenant/client/subdomain, independent login/directory credentials, hosted SSPR mode and validated MFA keyring/issuer. These secrets resolve through environment or pinned Key Vault references without fallback. Supabase credentials are conditional on selecting Supabase authentication/storage. Request identity is never cached in the process factory. Browser routes, delegated reset, native logout, MFA and protected security management are mounted; legacy credential APIs reject Entra password input. Body parsers are configuration-independent to avoid a startup configuration/vault import cycle.

See `azure-identity.md` for the current mounted contract and settings. Earlier component paragraphs below retain historical implementation details; their unmounted/unselected qualifiers are superseded by this section. Live tenant/browser/mail, complete hosted lifecycle policy and staging verification remain required.

## Architecture and contracts

One Next.js App Router deployment initially hosts frontend and backend. Backend feature classes live under `src/server/modules/`; interfaces define dependency boundaries. A composition root injects configured adapters. Framework route handlers/server actions validate input, resolve verified identity, call a service and return safe responses. React function components own presentation only. New feature modules carry scoped AGENTS.md.

IdentityProvider verifies the remote session and supplies an external subject and MFA assurance; ProfileRepository maps this to a stable internal UUID, role, status and unique client ID. AuthorizationService denies inactive profiles and requires admin MFA. Provider identity, application role and client financial identity are separate concepts. No caller-supplied identity grants access.

FinancialRepository operates under least-privilege database context. StorageProvider issues authorized private downloads and accepts validated/scanned uploads. EmailProvider sends through configured SMTP or a documented Azure adapter. AiProvider receives minimum read-only facts; RateLimiter uses shared database state. Implemented adapters must pass common behavioral contracts before advertised support.

## HTTP and security conventions

Protected routes derive identity server-side, disable shared caching and return safe errors. Mutations require same-origin validation plus framework CSRF protections where applicable. Public endpoints have bounded inputs and shared rate limits. Unauthenticated API requests return 401, forbidden requests 403, validation failures 400/422, unavailable dependencies 503 and limit failures 429. Never include provider payloads, tokens, credentials or internal stack traces in responses/logs.

Authentication uses Supabase's supported server-side session flow for the initial profile. Invite/reset redirects are restricted to the configured application URL. Public registration is disabled. Active admin MFA is checked for protected actions, not only in navigation. Sessions are never stored in global mutable service state.

`AuthCallbackService` validates bounded, unambiguous callback parameters, applies shared global/fingerprinted limits and invokes an injected `AuthCallbackProvider`. `SupabaseCallbackProvider` owns OTP/PKCE SDK operations and checks that successful responses contain a session with the matching user. The route receives only a fixed local destination, anchors it to configured APP_URL and sets private/no-store/no-referrer response headers. Optional flow IDs select the SDK's exact PKCE verifier slot. Composition does not expose a raw session SDK to routes. Supabase remains the only selectable authentication provider; Entra login/lifecycle/MFA and broader identity migration are still unimplemented.

The initial Entra building blocks share `EntraAuthority` for canonical CIAM issuer and endpoint validation. `EntraDiscoveryProvider` validates bounded discovery metadata/capabilities and returns only frozen approved endpoints, coalescing concurrent requests with five-minute success caching and a thirty-second failure cooldown; stale refresh failures do not fall back. `EntraTokenVerifier` verifies RS256 signatures against bounded/cached public keys and checks tenant-specific issuer, exact single audience, nonce, version, subject/object identity and token times. It returns only a frozen tenant/object-scoped `entra` identity at aal1; roles, email and MFA hints do not grant application authority. Neither component is wired to provider selection or a public token endpoint. `azure-identity.md` records endpoint constraints and the remaining browser cookie/routes, PKCE exchange, sessions, invitation/reset and trustworthy MFA work before Entra can be enabled.

`EntraLoginService` coordinates random browser-bound state/nonce/PKCE and fixed-origin code authorization through injected interfaces. Private PostgreSQL transactions store hashed state/binding/configuration proofs, expire after ten minutes and are atomically consumed before redemption. Advisory locking limits five active flows per browser across replicas; shared service limits and bounded maintenance cleanup apply. Native concurrency tests verify one winning consumer. Cookie/routes, sessions and lifecycle/MFA remain unwired; the provider stays unavailable. See `azure-identity.md` for the server-only contract and migration requirements.

`EntraCodeExchange` implements the injected adapter with oauth4webapi grant/response handling and independent JOSE signature verification. It binds the configured confidential client and callback, revalidates approved metadata destinations before sending the secret, and applies one bounded token/key HTTP operation without redirects, retries or credential fallback. Access/refresh tokens are discarded; only a verified aal1 identity returns. A composed SQL/discovery/OAuth/RSA test passes against intercepted endpoints. Runtime cookies, lifecycle and MFA remain required before provider selection; no public raw-token exchange endpoint is exposed.

`EntraSessionService` and `PostgresEntraSessions` implement opaque session issuance, hashed private storage, realm separation, eight-hour absolute/thirty-minute idle expiry, replacement and global application logout. Session functions require current active mappings; status/role/mapping changes revoke tokens without revival on reactivation. Profile/session locks precede expiry decisions. Narrow grants, a ten-active-session cap, secret-free lifecycle audits and bounded maintenance cleanup are tested, including native concurrency and expiry after lock waits. The profile repository accepts the database interface for composition/testing. The services compose with the unmounted HTTP controller below; runtime provider selection, lifecycle/MFA and live identity gates remain required.

`EntraHttp` and `EntraCookies` implement the unmounted HTTP boundary: same-Origin POST initiation/logout, browser-bound GET callback, current-profile authorization before session minting, fixed destinations and private/no-referrer responses. Host validation supports internal Next listener URLs through the preserved configured public Host, without trusting forwarded-host. Opaque host-only Secure/HttpOnly/SameSite cookies reject ambiguity; middleware mirror headers are stripped. A composed HTTP/discovery/SQL/OAuth/RSA/session/logout test passes with intercepted provider HTTP. Runtime route/provider/UI composition, browser/deployment verification, lifecycle and MFA remain required; Supabase stays the only selectable auth provider.

Entra MFA cryptographic classes implement context-bound AES-256-GCM seed envelopes with explicit key rotation, six-digit/30-second TOTP matching and high-entropy recovery-code digests. The class-driven service and private SQL functions now persist factors/challenges/recovery digests, enforce recent-primary enrollment, shared attempts and atomic database-clock/replay consumption, and rotate sessions with fifteen-minute elevation bounded by original expiry. Current confirmed factors determine assured session resolution. An unmounted same-Origin/Host HTTP controller validates bounded unique-field JSON, rotates secure cookies and revokes known minted sessions after response-installation failure. Unmounted React form source provides manual setup and one-time recovery-code acknowledgement. Self-service regeneration/removal now require recent primary sign-in and a fresh operation-bound factor proof; they revoke prior sessions/codes atomically, with regeneration issuing one replacement session and removal requiring new sign-in/enrollment. Runtime/route/form composition, browser verification and an approved all-proofs-lost/response-loss policy remain required. See `azure-identity.md`; cryptographic matching alone never yields aal2.

`EntraRuntimeFactory` centrally composes the implemented protocol/session/authorization/MFA/HTTP dependencies from explicit trusted constructor settings, database, telemetry and optional transport. Shared discovery/configuration never contains request identity: each `create(request)` returns a distinct identity/authorization pair with a copied header snapshot and current SQL verification. Unsupported password/headless logout/account-lifecycle operations fail explicitly without fallback. This source is unselected by `createServices`; environment/secret wiring, lifecycle, routes/UI selection and live gates remain required. See `azure-identity.md`.

The unselected `EntraDirectoryUsers` driver adds bounded, no-retry Graph customer lookup/create/readback with exact local identity binding and explicit uncertain-write errors. `EntraDirectoryCredential` pins application credentials to the configured tenant and Graph audience without ambient fallback. A private leased provisioning ledger now prevents automatic second creation after uncertainty, verifies stable tenant/email/object ownership and commits identity mapping atomically. Provider-specific invitation text distinguishes hosted recovery from Supabase single-use links; known SMTP acceptance is separate from uncertain status persistence. Explicit optional directory settings now compose the credential/driver/provisioning/invitation adapters through `EntraRuntimeFactory`; request scopes share only stateless account dependencies and retain separate verified authorization. Mounted runtime/secret selection, public hosted recovery and real first-password/permission/tenant/mail gates remain required. It is not a public account-creation endpoint. See `azure-identity.md` for API sources and operational constraints.

Hosted recovery source now persists login/recovery intent with one-use PKCE transactions and requests fresh provider sign-in. The unmounted recovery HTTP/form boundary collects no application credentials. A verified recovery callback commits own-realm prior-session revocation before minting a fresh aal1 session; admin factors remain enrolled and require fresh MFA. Transaction expiry is checked after acquiring the row lock, with a native regression test for late consumption. This does not prove a password changed or handle unobserved upstream recovery; runtime mounting, tenant/browser verification and upstream session policy remain release gates. See `azure-identity.md`.

Provider sign-out initiation now composes validated discovery/authority with fixed registered-return routing. The unmounted browser POST commits application revocation before clearing cookies and redirecting to the provider; local versus provider-initiation failures are reported separately. A native form source avoids AJAX-only sign-out. This does not prove remote completion or implement incoming front-channel single sign-out; actual tenant/browser/session policy and runtime selection remain required. See `azure-identity.md`.

API capability groups: auth (login/logout/reset/callback/MFA), admin clients, investments/snapshots, report upload/download, offers/notifications, client portfolio/history, support chat/contact and dependency health. Concrete operations and validation schemas are added with their phase, retaining these authorization contracts.

Account invitation/reset subjects receive the public company name from the backend composition root through constructor injection. The service requires a nonempty name of at most 200 characters and rejects control characters before provider or email calls. No brand name is accepted from invitation request input. Authentication factor issuer labels are independent of public copy; changing a company name does not rotate or rewrite enrolled MFA factors.

## Data and financial rules

PostgreSQL is the portable engine. Internal profile UUIDs are primary ownership keys; provider subjects have unique mappings. Financial records reference a client profile and acting admin. Use NUMERIC for persisted money and exact decimal calculations; never binary floating point for financial computation. Every value has an explicit ISO currency and reporting date.

Database connection settings are explicit driver fields with verified TLS/hostname defaults, optional public CA PEM and only a matching sslmode URL option. Arbitrary URL driver/file/identity overrides are rejected; plaintext is explicit local development/test only. Transaction identity is SET LOCAL, and uncertain commits/failed cleanup evict the connection. See `database-verification.md` for the policy and twenty-two real PostgreSQL 17.11 checks, distinct from hosted SQL and live provider verification.

Simple reported return is `(reported value - recorded adjusted cost basis) / recorded adjusted cost basis * 100`. P/L is value minus adjusted basis. Basis must explicitly account for contributions/withdrawals; this is not annualized, time-weighted or money-weighted return. Missing/nonpositive basis produces no return percentage. Do not combine currencies without an explicit dated conversion source. Charts use stored snapshots only. Corrections preserve previous records and actor/time/reason history; archive instead of destructive deletion.

Tables cover profiles/provider identities, investments, portfolio snapshots, private report metadata, offers, notifications, audit logs, isolated chat sessions/messages and shared limits. Constraints validate ownership, status, amounts, dates and unique IDs. RLS denies anonymous and cross-client access. Financial mutations and their audit evidence share a transaction. Supabase-specific auth context must have a tested equivalent before Azure PostgreSQL is supported.

Reports use generated storage object keys rather than user-controlled paths, PDF-only initial upload policy, bounded sizes and signature validation. Malware scanning is required before production report availability. Short-lived signed URLs are bearer capabilities; already-issued links may remain valid until expiry. New links require current active-account authorization.

## Configuration and operations

Azure platform monitoring has an offline-checked template for replica absence and ingress 5xx counts, scoped to one existing web application and an operator-owned action group. Rules default disabled and do not create recipients; receiver testing/enablement requires applicable notification authorization. `azure-monitoring.md` defines observations, missing-data limits and incident response. A selectable private OpenTelemetry operational-event adapter now exports the fixed pool/session/request-error catalogue to an approved Azure Monitor endpoint, with bounded queues, filtered fields, no automatic request/SQL instrumentation, no offline persistence and no redirects. Explicit managed-identity credential composition and bounded fixed-scope token acquisition are now implemented locally; hosted profiles reject Azure CLI and token failure cannot fall back to unauthenticated ingestion. Independent availability checks, live token/ingestion verification, complete dependency/scheduler/backup alarms and verified live ingestion/notifications remain required. See `azure-monitoring.md` for configuration, preview dependency and lifecycle limits.

The optional Azure storage infrastructure template creates StorageV2 and two private containers, disables Shared Key/anonymous access, enforces HTTPS/TLS and Blob encryption, and sets explicit redundancy and Blob/container soft-delete retention. It preserves authenticated public endpoint reachability for direct report SAS downloads, emits only resource names/IDs, and does not migrate objects or register database storage locations. See `azure-storage.md` for output mapping, retention boundaries and actual restore/RBAC gates.

Server-only validated settings select provider adapters. Initial targets: Supabase Auth/PostgreSQL/Storage, SMTP, optional OpenAI, PostgreSQL limits, console telemetry and local scheduling. AI disabled mode is disclosed FAQ-only behavior. Hybrid Azure Blob, independent Azure AI and Key Vault secrets adapters are implemented and locally contract-tested; real Azure verification remains pending. SMTP remains the selected email option for Azure hosting; ACS Email retirement is recorded in the project brief. Other Azure adapters are unsupported until implemented, and the complete Azure profile requires staging evidence. No implicit paid failover. See `azure-storage.md`, `azure-support.md` and `azure-secrets.md` for their exact contracts and live gates.

`RuntimeConfigurationLoader` asynchronously resolves the selected `SecretProvider` before final `ConfigurationService` validation and dependency composition. It publishes only a complete immutable configuration snapshot and shares one success/failure promise per loader instance. Key Vault uses allowlisted pinned references and explicit managed credentials, with no environment-secret fallback or mutation of process.env. Root Next instrumentation awaits configuration; server entrypoints and same-origin checks await the same API. Proxy runtimes may resolve independently. Rotation/recovery requires a coordinated restart; cached values are not continuously revalidated against the vault. Build profiles contain synthetic/environment settings only; production secrets are injected at runtime.

Development may run a public shell without dependencies only with explicit APP_ENV=development and SERVICES_ENABLED=false. All service-backed/protected endpoints then fail unavailable; this is not demo login or financial data. Enabled service profiles validate required settings before use. Staging/production cannot disable services. Secrets never use NEXT_PUBLIC variables.

Local, staging and production have separate credentials/data/storage. Migrations precede deployment with backup and rollback/forward-fix plans. Runtime health checks expose only safe status. Production needs HTTPS, restricted database/storage access, admin MFA, monitoring, backup/restore, incident response and legal/content review.

## Announcements and maintenance implementation

`AnnouncementService` and its PostgreSQL repository manage private `announcements` and retained `announcement_recipients` memberships. Admin MFA gates edits; recipient-scoped RLS gates published reads. Client DTOs omit other recipients. ## Offer image implementation

`OfferImageService` depends on typed image repository/storage/processor/scanner contracts. It scans PNG/JPEG input, normalizes via a credential-free native decoder child process, scans output and reserves an immutable private WebP object. Checksum readback and optimistic offer-version checks precede atomic attachment. Aborted objects cannot be published; cleanup never removes ready history.

Public image delivery ignores admin session authority, verifies the current published/valid attachment before and after byte retrieval, checks SHA-256 and serves no-store WebP. Global optimizer caching is disabled to preserve this authorization boundary. Admin preview/removal are separately MFA protected. ## Contact implementation

## Native recovery verification and operations

The native gate now uses a real snapshot-bound PostgreSQL custom archive and fresh CONNECT-quarantined target. ## Process shutdown contract

Node instrumentation installs a process-only `ServerShutdownCoordinator`; after Next HTTP/server cleanup it closes the existing pool (three-second soft deadline) and then telemetry (five seconds), without creating new resources. Concurrent calls share one promise; cleanup errors become fixed private status values, and service composition refuses new work during application cleanup. Azure exporter shutdown also shares one task and drains queued spans best-effort.

The version-pinned pnpm patch adds this boundary to Next 16.4.6 CommonJS/ESM cleanup with a ten-second outer hook deadline and retains original signal semantics. The bootstrap rejects incompatible/unpatched runtimes or manual signal overrides. Review/rebase/remove the patch on upgrade. Deadlines do not cancel arbitrary work, cover earlier request draining or prove hosted termination/ingestion; staging must verify actual platform grace and load. See `deployment.md` for compatibility, packaging and precise local proof boundaries.
