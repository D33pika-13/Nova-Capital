# Azure operational monitoring

Status: selectable operational OpenTelemetry source with local SDK/configuration tests, plus metric/HTTPS availability templates and offline policy checks. No metric rule, receiver, test notification, Azure Monitor arrival or incident response has been verified in a deployed environment.

## Signals and configuration

The foundation routes environment console/system logs to a dedicated workspace using Azure Monitor diagnostic settings. It retains 30 days, disables workspace key authentication and sets a bounded daily ingestion quota. Keep raw requests, credentials, signed URLs, contact details, financial records and chatbot questions out of logs. A daily quota is not a total cost cap and may stop log ingestion; missing logs are not proof of healthy operation.

`infra/azure/monitoring.bicep` defines two metric rules against one existing Container App in the same resource group. It references an existing operator-managed action group; it creates no email/webhook recipients, role grants, automated remediation or application secrets. The synthetic example keeps `alertsEnabled=false`. Configure separate names/resources for staging and production. Applying the template can incur monitoring costs even when notifications are disabled; review the live estimate and authorization before provisioning.

| Rule | Condition over five minutes | Severity | Interpretation |
|---|---|---|---|
| No replicas | Maximum observed `Replicas` below 1 | 1 | No observed web replicas during the window; this is not a dependency-health probe. |
| Server errors | Total `Requests` in `statusCodeCategory=5xx` at least `serverErrorThreshold` (default 5, range 1–1000) | 2 | Absolute ingress error count, including errors before requests reach the application. It is not a percentage. |

Rules evaluate every minute, retain Azure metric validation, use static thresholds and auto-resolve after recovery. They use Microsoft's documented [Container Apps metrics](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/supported-metrics/microsoft-app-containerapps-metrics) and [metric-alert resource contract](https://learn.microsoft.com/en-us/azure/templates/microsoft.insights/2018-03-01/metricalerts). Confirm dimension values and time-series aggregation against the actual resource; offline compilation cannot establish their runtime behavior.

These rules do not alert on missing metric data, missed maintenance schedules, failed email delivery, log-quota exhaustion, expired scanner signatures, storage/SQL backup failure or every permission/secret failure. Replica count does not establish readiness, and low traffic may produce no errors during an outage. The independent HTTPS template below supplies source for direct-ingress liveness; its live verification, scheduler success/freshness, dependency checks and backup/restore alarms remain required release work. The selectable operational OpenTelemetry adapter below is independent of these platform metric rules; neither source establishes live ingestion or notification delivery.

## Independent HTTPS availability

`infra/azure/availability.bicep` creates a Standard availability test plus its location-failure alert against existing same-resource-group Container App, workspace-based Application Insights and reviewed action group. Its synthetic example leaves `probeEnabled=false` and `alertsEnabled=false`; the rule requires both flags. This allows an authorized operator to verify probe results before separately authorizing notifications. No recipients, credentials, role assignments or remediation are created. Review current Standard-test/alert charges before deployment or enablement.

The target is derived from the existing app's managed ingress FQDN, with a fixed `https://…/api/health` GET and no credentials, query, custom headers, redirect following or dependent-resource downloads. Five public-Azure locations (East/West US, West Europe, Southeast Asia and Japan East) run every five minutes, with retry enabled and a thirty-second timeout. Validation requires HTTP 200, valid TLS with at least seven days remaining, and the exact `"mode":"configured"` response marker. A public-shell 200 cannot satisfy that marker. Health still explicitly reports `dependenciesVerified:false`: a passing probe proves configured HTTP liveness only. The alert evaluates every minute over five minutes, defaults to three failed locations out of five (range 1–5), severity 1 and automatic resolution. See Microsoft's [Standard test contract](https://learn.microsoft.com/en-us/azure/templates/microsoft.insights/2022-06-15/webtests), [location guidance](https://learn.microsoft.com/en-us/azure/azure-monitor/app/availability) and [availability alert criteria](https://learn.microsoft.com/en-us/azure/templates/microsoft.insights/2018-03-01/metricalerts).

Use this template only where the selected app's direct public ingress is the intended availability target. A proxy-restricted/private origin is expected to reject these external probes. Keep the test disabled there and prepare a separate approved public-proxy/private-network monitor; never widen the ingress allowlist merely to make it green. The template does not cover a custom domain, public-proxy route, missing test telemetry, authenticated journeys, database/storage/scanner health or scheduler freshness. Use the region of the existing Application Insights resource for `location`; confirm region/location support and endpoint reachability before applying.

Offline checks compile the template/example and validate TLS, exact target/content, redirects, request bounds, five locations, thresholds, scopes and disabled defaults, with invalid-parameter cases. Route tests verify configured/public-shell/failure responses without claiming dependency connectivity. No Azure test request, alert transition or receiver delivery has run. After authorization, deploy disabled, review the generated target/resources and receiver ownership, enable only the probe, record actual five-location success and a controlled staging failure/recovery, then separately enable/test notifications and record operator receipt. Restore healthy staging state and retain timestamped evidence. Missing probe data must be investigated separately from an available result.

## Staging verification and enablement

1. Deploy the reviewed foundation and workload after authorization. Confirm console/system logs arrive in the intended environment workspace with timestamps and retention. Review access permissions and inspect synthetic failures for accidental sensitive fields. Do not paste real log payloads into tickets.
2. Verify the existing action group's owners, enabled state and exact recipients. Review escalation coverage and any integrations capable of automated actions. A template reference alone does not establish receiver safety. Testing/enabling notifications requires applicable authorization to contact those recipients.
3. Apply metric rules disabled. Inspect actual metric definitions and dimensions in the target app. Confirm the configured rule scopes, `5xx` series, thresholds, costs and absence of global/cross-environment recipients. Wait for metrics to exist; do not bypass metric validation to make deployment succeed.
4. With approved synthetic staging traffic and controlled staging-only fault injection, record observed metric points, fired/resolved alert timestamps and exact action-group receipt. Test a no-replica window and a five-minute server-error threshold independently, then restore normal service. Do not scale production to zero or add an unauthenticated error/debug endpoint for testing.
5. Enable rules with explicit `alertsEnabled=true` after receiver/notification authorization. Run a separately approved notification test, verify actual receipt and record the responder/incident location. A successful Azure test action is distinct from an operator acknowledging it. Repeat after receiver or resource changes.

## Response and recovery

For a replica alert, inspect the current revision, platform events, digest and startup/probe status; investigate image-pull, identity, private DNS/vault connectivity and scanner readiness. Do not make private storage/vault public or grant broad roles to clear an alert. Compare the last reviewed release/configuration and use the documented compatible rollback if appropriate.

For a server-error alert, distinguish ingress failures from application safe errors, compare timing with releases and inspect safe operational codes. Check selected dependencies, database pool/TLS and current permissions. Preserve event times and resource/revision identifiers without copying credentials, report links or financial payloads. Verify public availability and an authorized synthetic private journey after recovery; an alert resolution alone does not prove feature health.

For credential compromise, restrict affected access and rotate pinned vault versions through the private runner, then restart/redeploy to refresh cached runtime configuration. Coordinate web/job maintenance references. For suspected client-isolation exposure, stop affected capabilities, preserve private audit evidence and follow the approved organization incident procedure; business/legal contact policies need owner review. No automatic destructive recovery or external messaging is authorized by this runbook.

Record deployment, metric observations, notification delivery, acknowledgement and post-recovery checks separately in `implementation-status.md`. Maintain the prior compatible image/configuration and rehearsed data recovery procedure; metric rules cannot restore data or undo emails/financial corrections.

## Application operational traces

`OBSERVABILITY_PROVIDER=console|azure_monitor` selects the server-only telemetry adapter; console remains the default. The Azure adapter uses the official `@azure/monitor-opentelemetry-exporter` with an application-owned OpenTelemetry provider. This follows Microsoft's [manual exporter composition](https://learn.microsoft.com/en-us/javascript/api/overview/azure/monitor-opentelemetry-exporter-readme?view=azure-node-preview). No global provider, automatic HTTP/SQL instrumentation, resource detector, request context propagation or exception recording is registered. Framework spans cannot enter this private provider.

For an approved existing public-Azure Application Insights resource, provide exactly these two fields, in order, without other fields or a trailing semicolon:

```dotenv
OBSERVABILITY_PROVIDER=azure_monitor
AZURE_MONITOR_CONNECTION_STRING=InstrumentationKey=<resource-key-guid>;IngestionEndpoint=https://<region>.in.applicationinsights.azure.com
APPLICATION_INSIGHTS_NO_STATSBEAT=true
```

Use the actual resource's approved regional endpoint; the placeholders above are not valid configuration. Extract only InstrumentationKey and IngestionEndpoint from a portal string that includes LiveEndpoint/ApplicationId; those other fields are not used. Custom/sovereign domains, arbitrary endpoints, credentials, ports, paths, query strings and duplicate/unknown fields fail validation. The connection setting is server-only and may use a pinned Key Vault secret reference. Leave its environment value unset when Key Vault is selected. The separate Statsbeat switch remains an environment bootstrap setting: the pinned exporter reads it directly and startup refuses export without it. The application never mutates process.env to activate the SDK.

The exporter now requires an Entra bearer token using the explicitly selected `AZURE_CREDENTIAL_MODE`. Hosted environments require `managed_identity`; `AZURE_CLIENT_ID` selects an optional user-assigned identity and omission uses the system-assigned identity. Development/test can explicitly select `azure_cli` with an existing operator login. No ambient credential chain or key-only ingestion fallback is used. The instrumentation key still selects the resource in the connection setting/envelope.

Grant the intended ingestion identity **Monitoring Metrics Publisher** at the exact Application Insights resource scope, following Microsoft's [Entra authentication guidance](https://learn.microsoft.com/en-us/azure/azure-monitor/app/azure-ad-authentication). Coordinate disabling local authentication on that resource with an authorized operator and verify rejection of unauthenticated ingestion in staging. The optional `access.bicep` telemetry selector prepares that exact resource-scoped publisher role for the web identity. Its default is console and it references an existing Application Insights resource. Applying the role, reviewing local-auth policy and verifying actual acceptance are external deployment gates.

`AzureMonitorCredential` accepts only the pinned exporter's exact public-Azure scope `https://monitor.azure.com//.default`; it refuses multiple/unselected scopes, tenant/claims challenges and pre-cancelled requests. One token acquisition has a three-second deadline, cancellation propagation and generic errors. Tokens must contain bounded printable ASCII and expire more than thirty seconds in the future; returned credential metadata is discarded. A late/hung/error/null/malformed/expired response cannot become an unauthenticated send. The transport also requires a bearer header and rejects 401/403 before SDK challenge processing. Token and HTTP deadlines are separate; the batch processor's four-second timeout may discard a batch while the bounded underlying attempt finishes. Hosted shutdown/drain needs staging verification. Use a separate existing resource per environment and review ingestion costs/quotas/retention before enabling export. Configuration alone neither creates Application Insights nor grants access. The workload template now accepts typed authentication and telemetry selectors with pinned Key Vault references. `workload.entra.example.bicepparam` demonstrates Entra/Azure Blob/Azure Monitor without Supabase credentials; it contains synthetic values and is not a deployment result.

The fixed event catalogue is `database.pool_error`, `auth.session_cleanup_failed`, `application.request_failed`, `application.started` (reserved for explicit lifecycle use), `maintenance.batch_completed`, `maintenance.batch_failed` and `maintenance.batch_unconfirmed`. Current pool/session cleanup dependencies use the selected adapter; Next's request-error hook emits only a fixed failure event and ignores the supplied error, request and context. Allowed attributes contain enumerated provider/status values, maintenance-only server-derived `nova.maintenance_origin=admin|scheduler`, and an optional finite duration from 0 to 60,000 milliseconds. Unknown events/attributes/values are discarded, including emails, subjects, tokens, raw errors, URLs, SQL and financial records. The resource identifies only the fixed service and configured environment; the Azure SDK may add its standard role/instance and SDK metadata. No success event proves service availability.

The provider uses explicit always-on sampling only for this small operational catalogue, independent of inherited sampler settings. It has a 256-span queue, batches up to 32, a five-second schedule and a four-second export timeout. HTTP calls have a three-second timeout and zero pipeline retries. Requests are restricted to the selected origin's POST `/v2.1/track`; redirect responses are rejected before the exporter's own redirect handler can follow them. Offline disk persistence is disabled. Burst pressure, process termination or outages may lose telemetry. Event recording never waits on network; export failure cannot change authorization or application responses. Explicit `flush` and idempotent `shutdown` are available. Node instrumentation installs the process shutdown coordinator; the pinned Next cleanup patch awaits it after HTTP/Next cleanup, closing the database pool before stopping telemetry. Concurrent provider shutdown calls await the same task. Local SDK tests prove queued spans export on shutdown without a separate flush through an intercepted transport. The isolated production package probe verifies cleanup order with private fixture sinks, both signals and bounded/redacted failure. It does not prove remote ingestion. See [runtime cleanup budgets and upgrade rules](deployment.md#shutdown-and-runtime-upgrades); reliable hosted termination/drain remains a staging gate.

Startup validates/constructs the selected adapter before serving. Stateless dependencies are shared per process using a configuration fingerprint, including across equivalent bundled configuration snapshots. Changed telemetry configuration requires restart. Repeated process contexts/replicas have independent queues. Console remains available only when explicitly selected; a malformed Azure selection does not silently fall back.

Local tests use an in-memory exporter and an injected HTTP transport around the real Azure exporter to inspect payloads, reject redirects, bound queues, validate configuration and enforce secret loading. They do not contact Azure. Live ingestion/query evidence, access/retention/cost controls, actual managed-identity token acquisition/ingestion, representative load/drop behavior, hosted shutdown/drain and operator-received alerts remain release gates. The SDK exporter is a pinned preview package; review its support/API status before release. Scoped overrides patch its logs dependency's old OpenTelemetry core/resources; see [the baggage allocation advisory](https://github.com/advisories/GHSA-8988-4f7v-96qf) and revalidate/remove overrides after upstream resolves patched versions.

## Scheduled-work alerts

`infra/azure/scheduler-monitoring.bicep` adds two disabled-by-default log alerts using an existing workspace, Application Insights component, dedicated user-assigned query identity and operator action group. No identity, recipient or role assignment is created. Confirm the selected component actually sends to the selected workspace, use that workspace's region, and grant the dedicated identity reviewed least-privilege query access before deployment. Do not reuse web/job identities or substitute a broad runtime role. Query rights and permissions to assign/use the identity require independent live verification; template references do not grant access. Review [Microsoft's log-alert identity and query guidance](https://learn.microsoft.com/en-us/azure/azure-monitor/alerts/alerts-create-log-alert-rule) before authorizing these existing-resource dependencies.

The application emits provenance only after scheduled bearer or admin MFA authorization. It derives `scheduler` from the internal scheduled path and `admin` from the verified admin path, never request fields. Console preserves only those enumerated maintenance values; Azure places them in `nova.maintenance_origin`. The real SDK's intercepted envelopes establish `RemoteDependencyData`, role `nova-capital`, fixed names/status/provenance and success flags. Its standard metadata metric is separate. The log query targets the documented [AppDependencies schema](https://learn.microsoft.com/en-us/azure/azure-monitor/reference/tables/appdependencies), filters the exact component ID, fixed role/provider and scheduler provenance, and excludes future event times. The component ID is base64-encoded in the generated query to avoid string-quoting ambiguity. Each environment needs its own component; the template tag alone does not partition telemetry.

| Alert | Evidence and condition | Limit |
|---|---|---|
| `scheduler-no-success` | No committed `maintenance.batch_completed`, successful, `ok` scheduled row within `staleAfterMinutes` (default 45, range 5–1440). | A stopped job, failed batch, dropped export, ingestion outage or clock error can produce the same signal. |
| `scheduler-failed` | At least one failed or unconfirmed scheduled outcome in the last five minutes. | A lost/delayed event can be missed; a later successful batch does not erase an observed failure inside the window. |

Both evaluate every five minutes with severity 1 and automatic resolution. They summarize without grouping into one numeric `Evidence` row and stamp that aggregate with query observation time, preserving zero evidence when the existing table has no matching rows. `Maximum` measures that numeric column, rather than counting the aggregate row. The explicit query lookback is also the rule override; missing-success age uses a strict greater-than cutoff, matching the database status's stale-at-boundary policy. Align minutes with `MAINTENANCE_STALE_AFTER_SECONDS` and the actual cadence plus startup/ingestion margin; hourly jobs need a larger reviewed interval. Notification timing includes evaluation/ingestion delays. These are observations of telemetry, not proof of dependency health or end-to-end job completion/backlog drain.

The private SQL ledger and admin operations view remain authoritative for committed outcomes and recovery boundaries. Cloud lookbacks do not inherit owner quarantine boundaries: prior events may remain in the window after restore. Verify a new post-recovery scheduled ledger entry and telemetry arrival before rearming operational monitoring. Auth rejection produces no success heartbeat; manual runs, unknown provenance and missing legacy provenance cannot satisfy these rules. Ordinary SQL failures remain distinct from unconfirmed transport/commit outcomes; do not blindly retry an uncertain operation.

Offline Bicep compilation/policy checks verify parameters, identity/scopes, bounded windows, fixed query filters, zero-evidence aggregation and retained Azure query validation. They do not execute KQL or establish table/identity access. `skipQueryValidation=false` intentionally requires a usable schema; absent tables or invalid query access must be resolved rather than bypassed. The resource API is [scheduledQueryRules 2023-12-01](https://learn.microsoft.com/en-us/azure/templates/microsoft.insights/2023-12-01/scheduledqueryrules).

After cost/resource/notification authorization, first verify scheduled and admin envelopes arrive separately and query their real workspace rows. Test both queries on an empty matching interval, recent scheduled success, admin-only success, failed/unconfirmed work, another component and delayed evidence. Deploy disabled with the reviewed query identity; prove its effective access and Azure query validation. In synthetic staging, stop the approved schedule long enough for the missing-success alert, restore it and record resolution; separately exercise a controlled ordinary failure and confirm its failed ledger entry. Do not add a public fault endpoint. Enable notifications only after receiver review and separately approved delivery tests; record actual operator receipt. Live queries, alert transitions/health and delivery remain release gates. No template or runbook step authorizes resource creation or external messaging by itself.
