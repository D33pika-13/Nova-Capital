# Entra identity implementation

Status: Entra is selectable in source with `AUTH_PROVIDER=entra`. Configuration, server-only environment/Key Vault secret loading, request-scoped composition, browser routes and conditional pages are implemented. Supabase remains the default. Protocol/database tests use synthetic identities and intercepted provider responses; no actual application tenant, app registration, consent, browser session, mailbox delivery or live Microsoft token has been verified. This source profile requires staging verification before release.

## Runtime selection and setup

Apply all migrations through `20261111001300_entra_hosted_recovery.sql` before enabling the profile. Set `SERVICES_ENABLED=true`, a canonical HTTPS `APP_URL` origin, and the Entra settings in `.env.example`: tenant/client GUIDs, tenant subdomain, confidential login secret, MFA issuer, active encryption key ID and a flat JSON keyring containing one to three independent canonical base64url 32-byte keys. The active ID must exist; duplicate decoded IDs/material are rejected. Preserve old keys during coordinated rotation. Never copy CI canaries into deployment settings.

Directory invitation support also requires a separate directory client GUID/secret and explicit `ENTRA_RECOVERY_MODE=hosted_sspr`. Login and Graph credentials are independent; no ambient Graph credential fallback exists. The login secret, directory secret and complete encryption keyring are allowlisted Key Vault settings. Vault selection forbids environment-secret fallback. Supabase URL/service-role credentials are required only when authentication or storage selects Supabase; its publishable key is required only for Supabase authentication. Entra plus Azure storage requires no Supabase SDK session.

`AuthenticationFactory` selects one provider and creates request-bound identity/authorization objects. `createServices` shares only stateless process dependencies. The proxy refreshes Supabase cookies only for the Supabase profile. There is no cross-provider cookie or identity fallback.

Mounted entrypoints are POST `/auth/entra/start`, `/auth/entra/recover`, `/auth/entra/logout` and GET `/auth/entra/callback`. Unsupported GET/POST actions and Entra routes under the Supabase profile return 404; other HTTP methods use framework method rejection. `/api/auth/mfa` dispatches to the selected provider. Legacy JSON login/reset/password actions return `BROWSER_AUTH_REQUIRED` for Entra; JSON logout revokes local application sessions, while the native browser logout initiates provider sign-out. The legacy Supabase callback cannot exchange an Entra session.

Login/reset, MFA and logout UI select matching native forms/controllers. `/password` redirects Entra users to delegated recovery. MFA admins can regenerate recovery codes or remove their authenticator at `/admin/security`, with fresh proof required by the service. Disabled local shells expose no login forms. The conservative `accountLifecycle:false` capability continues to indicate incomplete end-to-end hosted lifecycle verification; it does not disable the selected browser and invitation entrypoints.

Real hosted initial-password/SSPR completion, all-proofs-lost recovery policy, provider logout/session policy, consent, registered URLs and browser/TLS/cookie journeys remain release gates. No cloud resources are provisioned by changing configuration.

## Earlier component evidence

The component notes below record their implementation stages. References to unmounted/unselected components describe those earlier stages; the runtime-selection section above governs current mounting.

## Implemented discovery boundary

`EntraAuthority` provides shared configuration validation for discovery and token keys. It derives one tenant-specific public-Azure CIAM issuer and discovery URL from explicit GUIDs/subdomain. Authorization, token and logout metadata URLs must remain at that origin, using only the selected tenant GUID or matching `<subdomain>.onmicrosoft.com` path. Key URLs are restricted as described below. URL credentials, ports/origin changes, queries/fragments, other tenants and arbitrary paths fail closed.

`EntraDiscoveryProvider` fetches the exact derived discovery URL, rejects redirects, bounds response size to 64 KiB and applies a five-second fetch/body deadline (configurable up to ten seconds). It validates the exact issuer and advertised code/query, pairwise subject, RS256, openid/profile and confidential-client `client_secret_post` capabilities. Optional grant-type and PKCE advertisements must include authorization_code and S256 respectively when present; Microsoft metadata may omit those optional fields. Their omission does not authorize plain PKCE or password grants. The future browser flow must always request code with PKCE S256.

Only approved endpoint URLs, issuer, configured client ID and the selected authentication method leave this boundary in a frozen snapshot. UserInfo URLs, arbitrary document extras and unselected capabilities are discarded. Concurrent loads share one fetch; successful metadata expires after five minutes. Failed refreshes clear stale data and enforce a thirty-second retry cooldown. No stale-success or alternate-authority fallback exists. Local tests cover the endpoint/capability contract, concurrent cache behavior, refresh failure/recovery, input bounds and cancellation. These are intercepted metadata responses, not verification of an actual application tenant. Microsoft's [discovery reference](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc) and [code-flow reference](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow) inform this contract.

## Implemented token boundary

`EntraTokenVerifier` uses pinned `jose` 6.2.17 for RS256 signature and JWT claim verification. Its constructor receives an explicit public-Azure External ID tenant GUID, client GUID, CIAM subdomain and reviewed signing-key URL. Issuer is exactly `https://<subdomain>.ciamlogin.com/<tenant-guid>/v2.0`. Custom/sovereign domains, workforce/common issuers, arbitrary endpoints, redirects, URL credentials, queries and fragments are not supported. The key URL must use the same CIAM origin and either the selected tenant's or `common` discovery/v2.0/keys path. An actual tenant whose metadata differs needs a reviewed implementation change and tests, not relaxed endpoint validation.

Microsoft documents [External ID discovery locations and signature validation](https://learn.microsoft.com/en-us/troubleshoot/entra/entra-id/app-integration/troubleshooting-signature-validation-errors) and the [ID token claims](https://learn.microsoft.com/en-us/entra/identity-platform/id-token-claims-reference). Constructor values must come from reviewed deployment configuration and the validated discovery snapshot, never a caller token or arbitrary callback URL. The central factory below composes these boundaries, but mounted runtime provider selection remains disabled.

The verifier requires issuer, a single exact client audience, pairwise subject, immutable directory object ID, matching tenant, version 2.0, nonce and integer issued-at/not-before/expiry times. It checks optional authorized-party claims, rejects expired tokens without an expiry grace period and limits newly exchanged token age to ten minutes with thirty seconds of clock tolerance. Input is bounded to a 16 KiB JWT and a 32–128-character transaction nonce. JWT type, RS256 algorithm and a bounded key identifier are required; token-provided key URLs or embedded keys are rejected.

Successful output contains only `provider=entra`, tenant/object-scoped `subject=<tenant-guid>:<object-guid>` and `assurance=aal1`. Names/emails/roles/client IDs and MFA hints are not application authority. Internal provider mappings, account status, role checks and admin MFA remain separate. Never link accounts by email alone. The verifier does not create a mapping, profile or session, and does not persist tokens.

Signing keys are fetched only from the constructor-approved URL without access tokens, user claims or callback credentials. Response size is bounded to 256 KiB and 1–64 public keys; private/symmetric key material and ambiguous key matches fail closed. A deadline covers fetch and response-body reading (five seconds by default, maximum ten). Key caching lasts five minutes with a thirty-second unknown-key refresh cooldown. Cache expiry/rotation, invalid signatures, rejected claims, header key injection, malformed/oversized responses, hung fetch and stalled bodies are locally tested with intercepted HTTPS and generated synthetic RSA keys. The [jose remote-key resolver](https://github.com/panva/jose/blob/main/docs/jwks/remote/functions/createRemoteJWKSet.md) supplies signature-key selection; no custom signature algorithm is implemented.

## Implemented login transactions

`EntraLoginService` depends on provider-neutral discovery, transaction, code-exchange and rate-limit interfaces. It generates independent 256-bit state, nonce, PKCE verifier and initial browser-binding values. Authorization URLs use code/query, only openid/profile scopes, the configured exact HTTPS `/auth/entra/callback` URI and PKCE S256. Browser binding and the verifier never enter that URL. A valid existing binding can support parallel flows with separate state/nonce/verifier values.

Migration `20261111000800_entra_transactions.sql` creates private, RLS-enabled protocol storage. Runtime table reads/writes are denied; narrow fixed-search-path functions store and consume transactions. Only state/binding/configuration hashes are stored for those proofs. Nonce/verifier values remain private short-lived protocol material; do not include them in database/query/access logs or audit payloads. Database time fixes expiry at ten minutes. A per-binding advisory lock caps outstanding flows at five across replicas, alongside shared global/per-binding service limits.

The configuration fingerprint covers issuer/client, approved endpoints, selected authentication method and redirect URI. Callback requires exact single state/code or a provider refusal, rejects duplicate/unknown/malformed parameters and checks the initiating binding. A wrong binding/configuration does not consume the rightful transaction. Atomic DELETE/RETURNING commits before the injected code-exchange adapter receives the stored verifier/expected nonce. Replay, expiry or duplicate parallel consumption cannot trigger another redemption. Refusals and uncertain/failed exchanges consume the transaction and require new sign-in; there is no automatic retry/restoration. The coordinator does not create an application session or accept elevated provider assurance.

Existing scheduled/manual maintenance prunes at most 500 expired protocol rows per run; new transaction creation also prunes a bounded batch. Active rows are retained. Expiry denial is immediate regardless of cleanup cadence. The current maintenance response's `batchLimit`/`mayHaveMore` still describe offer expiry only, not the protocol cleanup backlog. In-account protocol cleanup is unrelated to financial archival/audit retention.

Local service/PGlite tests verify request construction, proofs, expiry, replay, configuration/browser isolation, provider refusals, throttling, private permissions and cleanup. Two additional native PostgreSQL checks prove the capacity lock and single winning consumer across real connections, wrong-proof/expiry denial and denied direct access. The composed test now injects the implemented code-exchange adapter with intercepted provider HTTP and real synthetic RSA signatures; these are not real browser/cookie/Entra login tests.

## Implemented code exchange

`EntraCodeExchange` implements the coordinator's `OidcCodeExchange` interface using pinned oauth4webapi 3.8.8 for [grant requests](https://github.com/panva/oauth4webapi/blob/main/docs/functions/authorizationCodeGrantRequest.md) and [response processing](https://github.com/panva/oauth4webapi/blob/main/docs/functions/processAuthorizationCodeResponse.md). It accepts only the server-owned, already-consumed transaction context. The validated state is passed through the library's callback validation as well; this does not replace the prior browser/configuration proof or one-use SQL consume.

Constructor settings bind one CIAM authority/client, exact HTTPS callback URI and a server-only confidential-client secret. Every exchange revalidates the issuer/client, authentication method and all endpoint URLs before transmitting that secret. Client authentication uses client_secret_post and library form encoding; no caller headers, additional scopes, fallback authentication or automatic retry are accepted. The code/verifier go only to the approved token endpoint. Client secrets, access tokens and refresh tokens do not go to signing-key endpoints, logs, storage or returned identity DTOs.

One operation deadline (default ten seconds, configurable up to twenty) covers token redemption, response reading and signing-key retrieval/verification. Token bodies are bounded to 64 KiB, key bodies to 256 KiB; requests reject redirects, non-200 responses and non-JSON content. Late responses and stalled bodies are cancelled. The OAuth library requires an ID token and validates response/nonce conventions. The existing `EntraTokenVerifier` separately verifies the ID token's real RS256 signature, issuer/audience/tenant/object/nonce/time contract. A syntactically valid JWT alone never grants identity. Each exchange creates a request-scoped verifier sharing the caller deadline; there is currently no cross-exchange signing-key cache in this adapter. Live latency/rate-limit/load checks remain required.

Only the frozen tenant/object-scoped aal1 identity returns to the coordinator. Access/refresh/ID token strings are not persisted or exposed by the adapter. A separate application-session service is implemented below, pending HTTP/runtime composition. The Entra client secret is a constructor dependency pending full runtime composition, not an enabled runtime setting/profile. Secret-canary scanning includes ENTRA_CLIENT_SECRET; CI/container definitions include synthetic canaries, not live credentials. Neither remote CI nor container execution has been observed for this change.

Tests use the actual OAuth and JOSE libraries with intercepted token/key endpoints. They cover exact form encoding, context/destination rejection before network access, signed-claim and signature denial, provider refusal/no retries, missing/malformed/oversized responses and one deadline across hung token/key bodies. A composed discovery → SQL consume → token redemption → RSA identity case proves replay causes no second redemption. It does not create an application browser session or prove Microsoft tenant compatibility.

## Implemented application sessions

`EntraSessionService` issues a new random 256-bit opaque token after verified first-factor identity. `PostgresEntraSessions` uses migration `20261111000900_entra_sessions.sql` to store only its SHA-256 hash in a private, RLS-enabled table. A narrow function creates a session only for an already mapped active Entra profile under trusted transaction-local identity context. Unknown accounts are not automatically enrolled. First-factor admin sessions stay aal1 and fail the existing MFA gate; callers cannot request an elevated session.

The realm fingerprint binds issuer, client ID and application origin. Lookups/revocation require both the token proof and matching realm. Stored ownership freezes profile, identity mapping and subject; every lookup rechecks the active current mapping/profile through fixed-search-path functions. Runtime direct table access is denied. No token/profile/role supplied by a browser is session authority. Service/repository objects cache no request identity or cookie values.

Database time enforces eight-hour absolute expiry and thirty-minute idle expiry. Valid lookup touches idle activity without moving absolute expiry. Profile/session locks are acquired before checking time so a request blocked past expiry cannot return an earlier valid decision. A profile lock serializes issuance/global logout; at most ten active sessions per profile/realm are retained, with oldest excess sessions revoked and audited. Raw tokens never enter session/audit tables or logs. Audit entries contain session UUID, actor, provider and creation/revocation metadata, not token hashes or provider token payloads.

Replacement revokes the prior browser token before issuing a fresh one; a failed replacement does not restore it. Logout can revoke all sessions belonging to the proven profile in that application realm. An expired or previously revoked token cannot revoke later sessions. Suspension/deactivation, role change or identity-mapping change revokes affected sessions transactionally. Reactivation or restoring a mapping cannot revive old tokens. Mapping deletion removes its private sessions. Local application revocation does not establish remote Microsoft SSO logout or continuous upstream account revocation; those remain integration/lifecycle gates.

Maintenance prunes up to 500 revoked/expired/idle-expired session rows per run, retaining current active sessions and separate audit evidence. Apply the session migration before deploying the changed maintenance repository. Expiry/access denial works even if cleanup is delayed. These fixed session lifetimes and concurrent-session policy need operator review before release. The storage design follows [OWASP session-management guidance](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html); actual browser cookie behavior still requires verification.

Local tests exercise creation, real profile authorization/RLS, tenant/app isolation, unknown/inactive accounts, first-factor admin denial, rotation, global logout, idle/absolute expiry, non-revival after status/role/mapping changes, capacity, bounded cleanup and fail-closed store behavior. Two native PostgreSQL cases verify concurrent revocation, account reactivation and expiry after a held session lock. These tests use seeded synthetic Entra mappings; no real directory account or browser session was created.

## Implemented HTTP/cookie boundary

`EntraHttp` coordinates the implemented flow/session services, current profile repository, cookie adapter and fixed operational telemetry through injected interfaces. It is a controller for future thin Next route handlers, not an enabled route/profile. Initiation and logout require POST, exact configured Origin and empty bounded input; method/origin/parameter rejection occurs before identity operations. Callback uses GET at the exact `/auth/entra/callback` path and requires the browser-binding cookie before redeeming a code. Protected destinations and error redirects are fixed application paths, anchored to configured application origin.

The boundary checks public Host against configured application origin. Next may expose an internal listener URL behind a proxy; Host is used when present, with request URL host as a fallback for Web Request contexts. It does not derive trust from forwarded-host headers. Actual ingress must preserve the expected public Host and enforce HTTPS/restricted origin access; this has not been tested in Azure. Both configured application/authority origins are HTTPS, and outgoing authorization redirects must stay on the configured CIAM authority's authorize path.

`EntraCookies` accepts only the selected opaque cookie values, bounds the raw header to 16 KiB and rejects duplicate/quoted/encoded/malformed selected cookies. Cookies are host-only `__Host-nova-entra-binding` and `__Host-nova-entra-session`, with Secure, HttpOnly, SameSite=Lax, Path=/ and high priority. Binding lasts ten minutes and is retained across callbacks for other outstanding established-browser flows. Session cookie lifetime is capped at eight hours and remaining server expiry; the server separately enforces idle/absolute/session-revocation policy. Cookie tokens do not appear in JSON, redirect destinations or telemetry. The adapter strips NextResponse's internal middleware cookie-mirror header and emits credentials only through Set-Cookie. This adapter is specifically for route responses, not middleware.

Callback checks the verified identity's current active application profile before issuing a session and routes first-factor admins to MFA. Invalid callbacks preserve an existing session. Once a valid login attempts replacement, failure clears the possibly revoked browser session cookie. If installation fails after minting, the new session is revoked where possible; a cleanup/telemetry failure cannot expose dependency payloads or prevent a safe error redirect. Initiation parameter rejection preserves cookies; malformed cookies on a same-origin initiation are cleared for retry. Logout revokes the proven own-realm sessions before clearing cookies; unconfirmed revocation returns an unavailable response rather than a success claim. The browser provider-sign-out initiation below is now implemented; actual provider completion and cross-application single sign-out remain unverified.

Local HTTP/cookie tests verify methods/Origin/Host, minimal input, redirect restrictions, safe errors, header/token privacy, recovery, account mapping/MFA routing and failed cookie installation cleanup. A composed test now runs HTTP-shaped initiation/callback requests through intercepted discovery/token/keys, real synthetic RSA signatures, PGlite state and application sessions, verifies cookie-authenticated identity, denies replay without erasing the current session and verifies logout/reuse denial. It creates no live browser/TLS/cookie-jar or Microsoft session. Native PostgreSQL session checks remain separate earlier evidence; no SQL changed for this boundary.

## Implemented MFA cryptographic foundation

`MfaSecretProtector` encrypts 160-bit authenticator seeds with AES-256-GCM. Each envelope has a fresh 96-bit nonce and authenticated version, key identifier, application realm, profile and factor context. The explicit keyring permits one active key and up to two retained rotation keys; malformed/noncanonical keys, duplicate key material, unknown identifiers and authentication failures fail closed. No plaintext or environment fallback exists. Intermediate decrypted byte buffers are cleared on success and authentication failure; JavaScript strings do not provide a memory-erasure guarantee.

`MfaAuthenticator` uses pinned otplib 13.6.0 with six-digit SHA-1 TOTP, thirty-second periods and one period of allowed drift. Independent RFC 6238 Appendix B vectors verify the six-digit policy. Provisioning uses an otpauth URI containing an internal profile identifier rather than an email address and does not contact a QR service. The matched time step is passed to the database flow below for atomic replay checking; matching alone does not consume it or elevate a session.

`MfaRecoveryCodes` generates ten independent 128-bit recovery secrets and context-bound SHA-256 digests. The database flow below persists only digests and consumes each once. The keyring is an injected constructor dependency: `ENTRA_MFA_ENCRYPTION_KEYS` currently names a validation error, not a selectable runtime environment setting. First-factor identities remain aal1. The unmounted HTTP/form source below implements response delivery. Complete runtime composition, all-proofs-lost recovery policy and browser/provider verification are still required before Entra selection. The self-service lifecycle below requires an existing factor proof.

## Implemented persistent MFA and step-up

`EntraMfaService` and `PostgresEntraMfa` compose the cryptographic classes with migration `20261111001000_entra_mfa.sql`. Every operation proves ownership through the current opaque session cookie hash and realm; current active admin status and exact identity mapping are checked by narrow security-definer functions. Direct table access and internal lock/limit helpers are denied to the application role. One factor per profile/realm is bound to the current mapping; status/role/mapping changes invalidate enrollment, recovery data, challenges and application sessions. Separate audit history retains lifecycle states without seeds, codes or token hashes.

Initial enrollment and pending-seed disclosure require primary application-session creation within ten minutes. Pending enrollment lasts ten minutes. Repeated setup within that interval returns the existing seed rather than replacing it. Existing confirmed setup returns only its factor ID. These are application policies that still require operational review and live verification; they do not constitute an organizational identity-recovery approval policy.

Setup and verification initiation share a durable ten-attempt/fifteen-minute budget per profile/realm across sessions. Verification creates a private hashed, session-bound challenge lasting at most two minutes, replacing any outstanding challenge for that session. Finish consumes that proof before denial checks and commits denials normally. Successful TOTP verifies the matched counter against database time (one thirty-second step either side) and requires it to exceed the factor's last accepted counter, under profile/session/factor locks. Recovery consumes exactly one matching unused digest. Enrollment stores ten distinct digests in the same transaction and returns plaintext recovery codes only after committed success; a lost response can be handled by authenticated regeneration below when an authenticator or unused recovery code remains. No automatic reissue or email bypass exists.

Successful verification revokes the old token and creates a fresh opaque session token atomically. The original creation/absolute expiry is preserved, idle activity is updated, and MFA assurance expires after fifteen minutes or earlier primary-session expiry. The assured session resolver returns aal2 only with an unexpired elevation and the current confirmed factor/mapping. Expired elevation falls back to aal1; caller-supplied assurance still cannot mint an elevated session. The self-service regeneration/removal lifecycle is implemented below; neither an old elevated cookie alone nor an arbitrary token claim authorizes it.

Maintenance now removes up to 500 expired challenges, 500 expired pending factors and 500 attempt windows older than twenty-four hours per run, with locked rows skipped. Confirmed factors/recovery records remain until explicit lifecycle invalidation. Apply the MFA migration before deploying the changed session and maintenance repositories. Offer-expiry response counters do not describe authentication cleanup backlog.

Ten service/PGlite tests cover enrollment/real admin authorization, encryption/digest/audit privacy, token rotation, realm/session/client denial, private permissions, freshness, expiry/replay, attempt limits, recovery single use, elevation expiry, invalidation and cleanup. Two additional native PostgreSQL checks verify one winner for concurrent TOTP and recovery attempts and a valid recovery proof expiring while blocked on a factor lock. These are service/database tests, not real browser, Microsoft tenant or delivered recovery-code checks. The HTTP/form source below is unmounted; no selectable Entra runtime profile has been enabled.

## Implemented MFA HTTP boundary and form source

`EntraMfaHttp` is an injected, unmounted controller intended for the provider-neutral `/api/auth/mfa` route. The existing mounted route still serves Supabase. The controller accepts POST only, exact configured Origin/public Host and exact path without query/fragment. Internal Next listener URLs require a preserved configured public Host; forwarded-host is ignored. Bodies are UTF-8 JSON of at most 1 KiB with a three-second read deadline, string-only flat fields and unique decoded keys. Unknown fields, ambiguous JSON, unsupported content encoding/type and malformed/missing session cookies are rejected before service calls. Actions are `setup`, `verify` with six digits, `recover` with a formatted recovery code, and the explicit lifecycle operations below; caller-supplied profile, factor, redirect or assurance fields are not accepted.

Setup emits only factor status/ID and a validated local otpauth URI for pending enrollment. Successful verification emits a fixed `/admin` destination and optional ten recovery codes, installing the rotated token only through the existing host-only Secure/HttpOnly/SameSite cookie adapter. Responses are private/no-store/no-referrer with nosniff; no token or framework cookie mirror appears in JSON/other headers. Denied codes preserve the current cookie. Uncertain rotation or failed response installation clears it; a known minted session is revoked, and cleanup/telemetry failures cannot expose secrets. No automatic retry or external QR service is used.

`EntraMfaForm` provides manual authenticator setup, six-digit and explicitly selected recovery entry, and an in-memory one-time recovery-code screen with a save acknowledgement before continuing. Fetches stay same-origin, reject redirects, bypass cache and are guarded against duplicate submission. Neither provisioning nor recovery secrets are written to browser storage. The form is not mounted on the current Supabase MFA page; runtime composition must select it with the matching controller. A lost enrollment response can use the authenticated regeneration flow below with a new authenticator code or another unused recovery code. There is no automatic seed disclosure or recovery-code reissue.

Fifty-seven HTTP tests cover request/cookie/provisioning/response/failure boundaries and compose real cryptography, PGlite enrollment, rotation, replay denial, recovery reuse denial and failed cookie-installation revocation. One presentation test verifies recovery-code acknowledgement rendering. This is not a real DOM interaction or browser/TLS/cookie-jar test; those remain required. SQL did not change for this boundary; native MFA concurrency/expiry results remain the previous increment's thirteen-check evidence.

## Implemented self-service recovery lifecycle

Migration `20261111001100_entra_mfa_lifecycle.sql` adds operation binding to private challenges. `EntraMfaService.regenerate` and `remove` require the current active admin session, primary session creation within ten minutes and a fresh TOTP counter or unused recovery code. An existing aal2 cookie alone is insufficient. The shared attempt budget, two-minute challenge expiry, database clock, ownership/mapping checks and profile → session → factor lock order remain in force. Finish rechecks recent-primary age after lock waits. Lifecycle proofs cannot be used for ordinary step-up or swapped between removal and regeneration; denied proofs are committed consumed without changing factor/recovery/session state.

Regeneration atomically invalidates every prior recovery digest, stores ten distinct new digests, revokes all prior sessions in the selected application realm and creates one rotated elevated session bounded by the original absolute lifetime. Other application realms remain separate. Removal revokes all sessions in the selected realm and deletes the factor, its recovery digests and challenges, with retained secret-free lifecycle audit evidence. It issues no replacement session. A new primary sign-in returns aal1 and requires fresh enrollment with a new factor/seed.

The unmounted HTTP controller accepts `{action:"regenerate"|"remove",method:"totp"|"recovery",code:"..."}` under the existing strict POST/Origin/Host/body/cookie boundary. Regeneration delivers new codes and a replacement secure cookie; removal clears both application cookies and returns only fixed `/login` routing/removal status. Invalid proof preserves the current cookie. Regeneration cookie-installation failure revokes its known minted session and clears the browser cookie. Unknown/uncertain completion is reported unavailable, without automatic retries.

`EntraMfaManagementForm` provides recent-sign-in instructions, explicit verification-method selection, password-style recovery entry and removal confirmation. Regeneration shows the existing in-memory one-time code-save acknowledgement. It is source only, intended for a future protected security page; the current Supabase runtime is unchanged. If a response is lost, a remaining authenticator or unused recovery code can authorize a fresh regeneration after sign-in. If all proofs are lost (including loss of the only replacement-code response after recovery-only regeneration), self-service stays denied. An operator-approved identity-recovery process, response-loss policy and live browser validation remain release gates; no email-only bypass, master recovery code or administrative override endpoint is implemented.

Six new service/PGlite cases cover successful lifecycle mutations, code invalidation, lost enrollment-response recovery with TOTP, realm/session revocation, recent-primary/confirmed-factor requirements, operation swapping and denied-input consumption. Ten new HTTP cases verify lifecycle schemas, cookie outcomes and cleanup, and the composed HTTP/SQL journey now exercises regeneration/removal. A second presentation case checks removal consequences/confirmation. Two new native PostgreSQL checks prove single winners for concurrent regeneration/removal and valid-proof denial after a factor lock crosses the recent-primary deadline. The native suite now has fifteen checks. None of this proves real Microsoft/browser behavior or enables Entra provider selection.

## Implemented dependency factory and request identity

`EntraRuntimeFactory` now centralizes the authority, bounded shared discovery, confidential code exchange, SQL one-use login coordinator, opaque sessions, profile authorization, MFA/lifecycle services and both HTTP controllers. It accepts explicit trusted `EntraRuntimeOptions`, a database interface, telemetry and optionally an injected HTTP transport. Tenant/client/origin, secret, keyring, issuer and deadlines are validated by their owning constructors before operations begin. The callback is derived from the validated application origin. Client credentials and copied MFA key material remain server-only dependencies; this does not add new environment settings or enable `AUTH_PROVIDER=entra`.

The factory may be reused for immutable process dependencies and discovery caching. Each `create(request)` makes a new `EntraIdentityProvider` and `AuthorizationService` with a copied request-header snapshot. Request identity is never stored on the shared factory/controller. Verification reads only the selected Entra cookie through the strict cookie adapter and consults the current private SQL session/factor/mapping/status state on every call. Cookie ambiguity is anonymous; database dependency errors are not converted into another identity provider or a successful session. Caller/header mutations after request-scope construction cannot switch its identity.

The returned capability descriptor explicitly distinguishes browser sign-in/application logout from unsupported password sign-in and full account lifecycle, with provider sign-out initiation distinguished from complete SSO behavior. Headless `signIn`/`signOut` refuse with browser-action errors; the HTTP controller owns protocol/cookie/revocation operations. Reset/password methods fail unavailable without forwarding credentials, sending mail or attempting a fallback. This factory is not yet selected by `createServices`, and existing Supabase auth/invitation/MFA/proxy behavior remains unchanged. Complete directory lifecycle, runtime secret/configuration wiring, thin routes/pages and browser/deployment verification remain necessary.

Sixteen factory tests compose intercepted discovery/OAuth endpoints, real synthetic RSA signatures, SQL sessions/RLS, authenticator verification, admin authorization, regeneration/removal and re-enrollment. They also verify client A/B/request isolation, current-status revocation without identity caching, shared discovery, unknown mappings, cookie ambiguity, explicit unsupported-method behavior, constructor denial without I/O, copied/mismatched keyrings and explicit private database-failure handling. The returned scope/capabilities are frozen. These tests do not provision an External ID tenant, mount an Entra route or prove real browser/cookie/account-lifecycle integration.

## Implemented customer-directory protocol foundation

`EntraDirectoryUsers` provides narrow Microsoft Graph v1.0 customer-account lookup, exact object-ID read and creation methods. The target is the External ID customer API, not B2B guest invitation: see Microsoft's [create-user/customer example](https://learn.microsoft.com/en-us/graph/api/user-post-users?view=graph-rest-1.0) and [identity-filtered listing](https://learn.microsoft.com/en-us/graph/api/user-list?view=graph-rest-1.0). The driver derives one local-account issuer from the configured tenant subdomain, uses only fixed public-Azure Graph users endpoints and returns a frozen minimal tenant/object subject plus normalized email. Enabled Member accounts must contain exactly one matching emailAddress identity for that issuer/email. Foreign, disabled, guest, malformed, ambiguous or paged results fail closed; no nextLink is followed, and no user/mail/UPN fallback is used. Email query literals are escaped and results are independently checked because a filter alone is not identity proof.

Each operation has one bounded deadline (default ten seconds, maximum twenty) covering token acquisition, HTTP and body reading; JSON is bounded to 64 KiB and decoded as strict UTF-8. Redirects, unexpected response URLs, status/type/body/schema failures and credential errors are rejected with private errors. No Graph request is automatically retried. Only a successful unpaged empty lookup means no account; transport/permission/replication failures do not become not-found. Graph list replication delays remain an operational limitation.

`createCustomer` sends one POST for a local email identity with an enabled account, an unknown high-entropy bootstrap password, forced password change and disabled password expiration. It reads the returned object ID independently to verify exact enabled identity before returning a subject. The bootstrap password is never returned, emailed or intentionally persisted; JavaScript strings cannot guarantee memory erasure. Network/server/invalid-response/readback/timeout failures after a possible POST are reported as `ACCOUNT_CREATION_UNCERTAIN`, requiring reconciliation rather than another automatic creation. Definitive known 4xx rejections are distinct. This driver does not implement idempotent account orchestration or imply that hosted first-password recovery is verified.

`EntraDirectoryCredential` constructs an explicit tenant/application client-secret credential against the fixed public Azure authority, disallows additional tenant overrides, restricts requested scope to Graph `.default`, disables SDK HTTP retries and unsafe/account-identifier logging, and never consults ambient managed/CLI credentials. SDK construction/scope contracts are tested through an injected builder; actual Microsoft credential exchange remains unverified.

Fifty-eight protocol tests cover fixed scope/endpoints, escaped filters, exact identity/ID binding, minimal output, ambiguity/disabled/foreign denial, input/credential rejection, transport/body/deadline limits, creation/readback and definitive-versus-uncertain outcomes without retries. Ten credential tests cover explicit construction, audience/tenant rejection, cancellation and no credential fallback. ## Implemented durable provisioning and hosted invitations

Migration `20261111001200_entra_provisioning.sql` adds a private RLS-protected ledger keyed by tenant and client profile, independent of application origin/client-ID changes. A unique tenant/email fingerprint prevents a new profile from taking over an unresolved earlier provisioning intent. Tenant domain, email fingerprint and any verified object ID are stable; changed profile email/domain or conflicting identity requires review. Narrow functions require current active admin MFA, lock actor/client rows, and check active client state before claiming, starting creation and committing a mapping. Two-minute leases are checked with database time after locks; superseded/expired workers cannot start a write or complete another worker's claim.

Ledger states distinguish read-only `checking`, committed create intent `creating`, reconciliation-only `unknown`, proven no-creation failure `rejected`, and verified/mapped `ready`. `EntraProvisioningService` first checks the existing directory identity. A missing account may create only from a live checking lease, after the one-use intent transition commits. A crash or uncertain response after intent leaves a durable barrier: lease expiry, process restart, another invitation ID and email duplicate-risk acknowledgement cannot authorize another POST. Reconciliation may only read and verify the directory result. A successful result and stable provider mapping commit atomically with secret-free audit history. Definitive credential/input/known rejection errors before any possible creation can return to a newly checked attempt; negative reads after an uncertain write cannot.

The ledger is retained without automatic expiry/deletion. A missing account after an uncertain write remains blocked until directory reconciliation or an operator-reviewed repair policy; no unreviewed override/automatic negative-proof timeout exists. Existing object IDs are reverified by exact read on later setup/reset requests; missing/disabled/reassigned directory accounts do not trigger recreation. Profile status/email changes between intent and outbound Graph may leave an external account to reconcile, but prevent mapping/email completion; no database lock is held across external HTTP and no automatic directory deletion is attempted.

No bootstrap password, email-bearing query string or false single-use-link claim appears in the Entra message. Hosted initial setup/forced-change/SSPR behavior is still an unverified live gate, and the provider is not selected by the mounted application.

Mail and account states remain separate. `ACCOUNT_PROVISIONING_UNCERTAIN` reports possible account preparation with no email attempt; the invitation attempt is failed preparation while the canonical provisioning ledger retains uncertainty. `DELIVERY_UNCERTAIN` means a send was attempted without confirmed SMTP acceptance. `INVITATION_TRACKING_UNCERTAIN` records known SMTP acceptance with an unconfirmed status save, without downgrading or blindly resending it.
