## Client announcements

After applying the versioned migrations, active admins with MFA use `/admin/announcements` to create, edit, publish, unpublish or archive a notice. A title, message and 1–200 explicit client recipients are required. Search by name, INV ID or email; search results are capped at 50, so refine the query to find additional recipients. A suspended or deactivated client may remain a recipient but cannot access the notice until reactivated. No email is sent by this workflow.

Clients use `/portal/announcements`. Only currently published notices addressed to their verified account are returned. Other recipient identities, admin metadata and other clients' read states are excluded from client DTOs. The inbox and management pages paginate in groups of 50. Unpublishing or archiving hides a notice on subsequent reads. A client may already have seen or retained content before it was withdrawn.

Each saved edit increments the announcement version. “Mark as read” acknowledges only the displayed version, using a server-generated timestamp. The current notice is unread if that version differs from its stored read version. Repeating an acknowledgment preserves its timestamp and does not create another audit update. An outdated acknowledgment returns 409 and asks the client to refresh. This records a client action; it does not prove that the person read or understood the message.

Recipient removal marks membership inactive; it does not delete the receipt row or audit history. Re-adding a recipient preserves the previous acknowledgment, which remains for an earlier version. Announcement edits, recipient changes and acknowledgments are audited. Admins can inspect how many currently included recipients acknowledged the current version; they cannot acknowledge on a client's behalf. No destructive delete is exposed.

## Expiry maintenance

Offer visibility always enforces UTC `starts_at <= now()` and `ends_at > now()` in database RLS, even when no scheduler runs. Maintenance changes only already-ended published offers to `expired`; it never publishes, extends, or changes offer content. It increments versions and preserves normal audit history. A scheduler uses no human identity and has a null audit actor. Manual runs identify the verified admin.

A run processes up to 500 due offers, with row locking and `SKIP LOCKED`. Its response is `{expiredOffers, batchLimit: 500, mayHaveMore}`. If 500 rows were changed, more work may remain. Repeated runs safely resume; a drained offer queue creates no duplicate offer-update audit events. Each committed batch retains its own operational outcome. Concurrent native PostgreSQL locking still requires staging verification.

The repository also prunes up to 500 expired private Entra login transactions and up to 500 revoked/expired/idle-expired application sessions in the same database transaction. It does not remove active requests/sessions, financial history or session audit evidence. Offer counts and `mayHaveMore` describe offer expiry only; subsequent scheduled runs handle remaining authentication cleanup. Apply all migrations through `20261111001400_maintenance_history.sql` before deploying the current repository. Entra is selectable in source; `azure-identity.md` records the separate tenant/browser/recovery gates.

- Manual: an MFA admin selects **Expire ended offers** at `/admin/offers`. The same-Origin `POST /api/admin/maintenance` has independent admin authorization.
- Local scheduler: start the integrated app, set `SCHEDULER_PROVIDER=local`, `APP_ENV=development` (or `test`) and a server-only random `CRON_SECRET` of 32–256 characters in ignored `.env.local`. Run `pnpm maintenance:watch`. It invokes the app once, then every 60 seconds after the previous invocation completes. Stop with Ctrl+C. Default public-shell mode cannot run maintenance because it has no connected database.
- Hosted scheduler: set `SCHEDULER_PROVIDER=external` and inject the same secret securely into the app and scheduler. Invoke `node scripts/run-maintenance.mjs` on the deployment scheduler's configured cadence, with `APP_ENV`, `APP_URL`, `SCHEDULER_PROVIDER` and `CRON_SECRET` supplied as environment values. Alternatively call `POST /api/maintenance` with `Authorization: Bearer <secret>`. Do not put the secret in query strings or command arguments. Cookie sessions do not authorize this endpoint.

The CLI uses HTTPS, allowing cleartext only to development/test loopback origins. It refuses hosted local/watch profiles, redirects and credential-bearing URLs. Each call has a 15-second timeout; at most ten batches (5000 offers) are drained per invocation. A failure exits nonzero for an external job and logs a safe error. Local watch logs failures and retries at its next interval. Logs contain counts and pending-work flags, never credentials. The server endpoint also rejects local scheduler mode in staging/production. Rotate the shared secret in both environments together and restrict scheduler network access at deployment.

The maintenance script is included in the standalone package; it uses Node's built-in APIs and does not require application secrets other than its scheduler credential. Run it with the approved environment. No hosted job, cloud resource or production schedule has been created.

## Durable run evidence and operator status

The maintenance repository now invokes one narrow `private.run_maintenance_batch()` capability. Its guard derives scheduler/admin origin from the trusted transaction identity. Admin batches retain the current verified actor; scheduled batches use no human actor. Clients, low-assurance admins and unmapped nonempty subjects cannot invoke it as system work. Caller input cannot name an alternate task, choose an actor or supply completion times.

Every confirmed batch records started/finished database timestamps, origin, terminal outcome and a bounded offer count in private RLS-protected `maintenance_runs`. A bigint identity provides deterministic insertion order for timestamp ties. An empty successful batch is still evidence. The capability catches ordinary inner cleanup/expiry errors in a subtransaction: partial writes and their audits roll back, then a generic failed record can commit in the outer transaction. The repository translates that committed result to safe `MAINTENANCE_FAILED` HTTP 503 after the transaction returns. SQL error strings, tokens, customer data and provider payloads are not stored in this ledger or DTO.

Connection loss, cancellation or uncertain commit can leave completion unconfirmed. Those paths must not manufacture a persisted failure or success. Fixed telemetry events distinguish `maintenance.batch_completed`, `maintenance.batch_failed` and `maintenance.batch_unconfirmed`; observability errors cannot turn committed work into an automatic retry. Ordinary row-update/audit idempotency still applies to subsequent runs. Ledger retention removes at most 500 records older than thirty days per batch, preserving business/audit records. Capacity, retention and missing-data alarms still require deployed verification.

Active MFA admins can read `GET /api/admin/maintenance` or `/admin/operations`. The backend and database independently recheck access. Responses are private/no-store and expose only UTC observation/completion times, outcome, bounded offer count, recovery boundary and freshness threshold. Direct history reads are denied to the application role. The page summarizes retained evidence; it is not an external-job control-plane report.

`MAINTENANCE_STALE_AFTER_SECONDS` is a validated server setting from 60 to 86,400 seconds, default 2,700 (45 minutes), and is available in the typed Azure workload connections. Configure it above the actual interval plus startup/drain margin; the default fits the template's fifteen-minute cadence. An hourly job needs a larger reviewed threshold, such as two hours, based on operational policy. Local watch normally runs once a minute. The backend compares database observation time against the latest scheduled terminal record: `never` means no retained eligible scheduled record; `failed` means the latest eligible batch has a confirmed failure; `stale` includes the exact configured age boundary; `backlog` is a recent completed batch with 500 expired offers; `current` means a recent committed scheduled batch. Offer backlog is a hint, and authentication cleanup may require later runs. A manual batch does not establish scheduler freshness. Inconsistent or future timestamps return safe unavailability.

The latest owner `AUTH_QUARANTINE` restore audit establishes a recovery boundary. Eligible scheduled records must have started strictly after that boundary. Earlier history remains intact and can no longer make the restored service appear current; a new scheduled batch is required. The native archive/restore rehearsal checks this along with authentication quarantine. The threshold and history prove database activity only; hosted scheduler execution, live dependency health, recovery completion, external email/file operations and operator notification remain independent gates.
