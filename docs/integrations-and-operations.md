## Configuration profiles and data separation

The existing staging profile selects Supabase/PostgreSQL/SMTP/FAQ/console/database scheduler/env secrets. `CONTACT_ENABLED=true` and `EDUCATION_ENABLED=true` use a private `CONTACT_HASH_SECRET` with separate HMAC namespaces; staging/production require `CONTACT_CLIENT_IP_HEADER=x-real-ip` behind the verified proxy. Education stores consented requests in a private MFA-admin inbox; it sends no automatic email or WhatsApp and makes no booking/payment.

Keep development, staging and production accounts, databases, buckets and secrets separate. `.env.example` is a blank, public-shell starting point. `.env.staging.local` contains private app settings; `.env.staging.operator.local` contains owner-only DB/operator access; `.env.staging.testing.local` contains synthetic test credentials. All three are excluded from Git. Neither the app process nor CI should receive owner DB credentials.

A Supabase dashboard login is not an app login. A GitHub account is not a Supabase account. An Auth user is not an application admin until correctly mapped to an active internal profile and MFA verified. Seed fixture subjects such as `synthetic-admin` are database test values, not usable password-login accounts.

## Bringing up the project on the owner’s machine

1. Clone the private repository after access is accepted. Install the Node version from `.node-version` and pnpm 11.25.0. Run `pnpm install --frozen-lockfile` so the Next runtime patch is applied.
2. Copy `.env.example` to ignored `.env.local`. `pnpm dev` with the default disabled services starts the public shell only; it does not create cloud resources or a test login.
3. For a connected test profile, obtain separate app settings through the credential handover. Set the canonical `APP_URL`, `SERVICES_ENABLED=true` and explicit provider selectors. Supply the least-privilege DB URL/CA, Auth/storage settings and SMTP settings. Run the configured scanner before testing uploads. Never copy production customer data into local fixtures.
4. For a new database, apply the reviewed ordered SQL migrations and provider-specific policies with an owner-only connection; use the migration instructions in `database-verification.md` and `deployment.md`. The existing staging project already has the Education migration. Do not blindly re-run seed data against an existing project. Configure private buckets and trusted Auth callbacks separately.
5. Bootstrap/verify the intended app administrator using the documented provider mapping and active profile; complete authenticator MFA, then test client A/B isolation and invitation/recovery capture. No real password belongs in migration SQL.
6. Run `pnpm lint`, `pnpm typecheck`, `pnpm test`, `pnpm format:check`, the production build and relevant package/secret scans. Use non-secret canaries for `pnpm check`; inspect `.github/workflows/ci.yml` for its complete synthetic settings. No real service secrets are needed for those isolated checks.
7. Repeat actual tests on the connected staging profile: login/MFA, invitation/reset capture, private report upload/download/denial, dated portfolio records/corrections, Education guest/client submit → MFA-admin inbox, contact capture and maintenance. Passing isolated local tests does not prove a new hosted provider setup.

For a packaged local start, `pnpm build` creates `.next/standalone`; `pnpm start` copies static/public assets and loads `.env.local` if present. `APP_HOST` controls the binding and `PORT` the listener. The private launchd staging copy described below is a separate deployment and is not updated by editing the checkout or by a GitHub push.

## Initial owner admin mapping

For a new owner-specific app administrator, first obtain the verified intended provider identity and use the authorized owner-only bootstrap process. The current portable schema stores the internal profile in `public.profiles` (`role=admin`, `status=active`, no client ID) and the exact provider Auth UUID in `public.provider_identities` (`provider=supabase`, `subject=<verified Auth user UUID>`). Check existing email/subject mappings before writing; do not change a client profile into an admin as a shortcut or reuse a synthetic seed subject. Record the authorized grant/audit, then complete the owner’s own password setup and authenticator MFA. The ordinary client-creation interface cannot bootstrap a new admin. This documentation does not execute that grant or authorize a newly identified person by itself.

## Current Mac staging operations

Inspect with `launchctl print gui/501/<exact-job-label>` and local health/port checks before restarting anything. The app/private env, Caddy and scanner can be restarted independently. A tunnel restart can replace the hostname, so do not restart it merely to deploy app code. Preserve graceful shutdown and wait until the exact job has stopped before bootstrapping it again. Use `deployment.md` for the current package/ports/rollback notes.

When a tunnel must change: obtain the new hostname, set the same canonical `APP_URL` in checkout and private runtime env, update Caddy’s allowed host, replace Supabase Site URL and both exact `/auth/callback` and `/auth/callback?next=/password` allowlist entries, deploy/restart the app/proxy, then test login/recovery/contact/Education. Retire the old callbacks. Use the newly verified link in tester communication; do not promise that a historical tunnel remains available.
